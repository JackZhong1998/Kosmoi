# System Prompt 迭代评测

评测对象：v2 System Prompt（加入用户修改协议 + 序章铁律）+ DeepSeek V4.1 Flash

## 相对 v1 改了什么

1. **用户修改协议**：选题、人物、情节、结局、文风、单段正文都可以用对话打补丁；必须给变更清单；禁止把旧约束丢掉重开项目。
2. **序章铁律**：正文必须先写序章；前 400–800 字内交出困境、角色用行动证明魅力、第一次真正选择、具体钩子。
3. **短篇规模**：允许序章 + 4 章做闭环，避免每次评测都要写十万字才能验证结构。
4. **恋爱互动禁区写死**：三个结局不能只换陪着的人。

## 短篇闭环样本《三十天，把店救活》

参考《完蛋了！我被美女包围了》的结构（共同困局、多角色、选择很快、反馈落到关系），不抄情节。

| 项 | 结果 |
|---|---|
| 三选题不换皮 | 通过：救店 / 包裹悬疑 / 老楼签字 |
| 推荐有共同主线 | 通过：三十天办屋顶演出或关店 |
| 序章钩子 | 通过：收铺电话 + 程知遥用赝品唱片立住 + 签/追问/办演出 三选 |
| 选项是做法不是去不去 | 通过 |
| 设计含序章卡、结局卡、状态表 | 通过 |
| 正文可解析进阅读器 | 通过（序章 start=p01） |
| 结局闭环 | 通过：n12a 办成了但店变了 / n12b 店关了人没散 / n12c 拿了钱输了人，死链为 0 |
| 正文汉字 | 约 1.5 万（短篇目标范围内） |

## 仍需下一轮迭代的点

- 长上下文后续章容易丢 `isEnding`，生成管线应把“缺节点名单”写进每一轮 user 消息（已做）。
- 关系向短篇仍要盯：数值别变成好感度排行榜，结局差异要落到店和人的命运。
